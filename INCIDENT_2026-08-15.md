# Incident: build 04 first flash — test fixture hung

**Date:** 2026-08-15, 09:25–10:45
**Image:** `moes-conv-v13-audited.zigbee` (= build 04, commit `b485043`,
sha256 `01c148be…`), served from the workstation at `<ota-server>:8093`
because the bench Pi was serving **stale, dangerous images** — its default
conversion file was build 01, the exact image that bricked a fixture on
2026-08-14.
**Outcome:** transfer perfect; firmware booted, joined, answered a full
configure pass; then **hung** (radio dead, PWM latched warm-orange) at
~10:22, ~3 minutes after install. Hang survived a user power cycle. Not
recoverable over the air. No other device affected.

## Diagnosis

**A deterministic hang, not a reset loop.**

- No `device_announce` at any point (not even on the boot that joined and
  answered configure).
- No periodic dips in the light over 30 s; probation/rescue would have needed
  only 6 reboots to latch — over 25 minutes elapsed with the light at full
  output, so **no reboots happened**.
- `MAC_NO_ACK` continuously: the radio is not in RX; a hung CPU with the radio
  in RX would still auto-ACK MAC frames in hardware.
- PWM hardware latches without the CPU → steady orange.
- Survived a power cycle → the hang is on the boot path or triggered by the
  same post-join traffic, deterministically.

Death occurred in the window between a successful configure (ZCL writes →
`zcl_reportingTab_save` → NV writes → flash sector erases) and a routine ZDO
active-endpoints request. A hard hang (not an exception: our handler calls
`SYSTEM_RESET()`, which would have produced reboots and eventually rescue
mode).

**What this is NOT:**
- not the key-scanner bug (that code is dead-stripped from build 04)
- not the factoryRst ordering bug (fixed; and that produced announces)
- not an image-format/CRC problem (bootloader installed and ran it)
- not a transport problem (flawless transfer)
- not the stock bootloader (it installed our image and our code drove the LEDs)

## What the safety net did and did not do

Rescue mode (this build's new mechanism) **never engaged — structurally
cannot engage on a hang.** It counts *reboots*; a hang produces none. This is
the documented residual risk (`FALLBACK_DESIGN.md` §4.1/§8) — but the sharper
reading is §5: **the hardware watchdog is the missing half.** With
`MODULE_WATCHDOG_ENABLE 1`:

> hang → 600 ms watchdog reset → reboot loop → probation counts → boot 7
> latches rescue → minimal join → OTA of build 05.

We sequenced "rescue mode first, watchdog second" and then shipped rescue
*without* the watchdog, on the theory that a reset loop was worse than a
hang. This incident is the counterexample: on a device whose only recovery
path is OTA, **a hang is the worst possible outcome** — a reset loop at least
presents a rescue-mode target. See the corrective actions.

## Positive results from today (they matter)

1. **The transport is solved.** 54 minutes, 200 KB, zero stalls, lqi 255. The
   bench unit's stalls were its RF, as suspected.
2. **The stock bootloader installs our image and our code boots** — again.
3. **The pin map is right on at least the warm-white channel** — the light
   rendered our 2200 K default. First LED evidence ever.
4. **Our ZCL stack joined and passed a full configure** on real hardware.
5. **The IEEE/identity chain held** — same `ieee_address` throughout, same
   z2m device entry, `supports_ota` intact.
6. **The audit's operational catch was real:** the bench Pi was serving
   build 01 (the image that bricked 2026-08-14's fixture) as the default
   conversion file. Had `rollout.py` been run with defaults, the next light
   would have been bricked by *old* code. Bypassed by serving from the
   workstation.

## Corrective actions

1. **Enable the hardware watchdog** (build 06), with the precondition from
   `FALLBACK_DESIGN.md` §5.2: add `drv_wd_clear()` inside
   `ota_newImageValid()`'s CRC loop in the vendored SDK, and record the SDK
   patch in `MOES_EDITING_GUIDE.md` §2.
2. **Pull the fixture** (ladder). Before anything else, take a full SWire
   **read** dump — flash *and* SRAM (reads are proven working, `SWS_DIV=110`,
   460800 baud; `dump/TLSR825xComFlasher.working.py`). An SRAM dump holds the
   stack/PC at the hang: that is the post-mortem. This unit becomes bench
   affected unit and the test bed for build 05/06 — it cannot be re-flashed over
   the air and SWire writes are broken on this silicon, so it needs the
   TB-03F programmer either way. **Buy the TB-03F.**
3. **Do not roll anything to the fleet** until the hang is understood. The
   remaining deployed stock fixtures are healthy and untouched.
4. **Build 05 exists** (`6464-0395-ffffffff-rescue05.zigbee`, commit
   `a72a2ae`): build 04 minus the colour-temperature change — the only
   behavioural change that had never run on hardware and the leading suspect
   for the hang. It has nowhere to be pushed right now; it is ready for bench
   affected unit, or for any light that ever latches rescue mode.
5. **Purge or rename the stale images on the bench Pi** (`moes-conv-v1`,
   `moes-conv-v12`, the 11013003/11023003/11033003 updates) so no tooling can
   ever serve them again. `rollout.py`'s hardcoded URLs must be updated in the
   same pass.

## Open questions for the post-mortem

- Did the user (or a Home Assistant restore-state automation) turn the light
  **on** around 10:19–10:21? The boot path leaves the light OFF; the orange
  implies a colour write after boot — either HA re-applying state on the
  fresh join, or a colour-temp report/configure side effect. That write is
  interesting: it exercised `tuyaLight_updateColor()` →
  `hwLight_colorUpdate_colorTemperature()` → `temperatureToCW()` shortly
  before the hang.
- Why no `device_announce` even on the boot that joined and passed configure?
  (The 2026-08-14 light announced on every cycle. If our stack announces only
  on *re*join, not first join, the announce-cadence gate is blind during
  exactly the window we care about.)
- Whether the hang is in the colour path (revert in build 05 would then fix
  it) or in NV/flash-erase handling during configure (which build 05 would
  *not* fix — the watchdog becomes the actual mitigation).
